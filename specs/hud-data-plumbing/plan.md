# HUDデータ整備 実装計画

## コンテキスト
ホーム/履歴/記録のHUDがダミー値に依存しているため、ドメイン側で進捗計算と集計を担うモデルとヘルパーを整備する。SwiftUI ターゲット（`my_traning_app`、`my_traning_appTests`）のみを変更し、新規モジュールの追加は行わない。

## アプローチ
1. **プランモデルの追加**
   - `Plan` / `PlanSuggestion` / `PlanProgress` を `Domain/Models` に追加し、目標メトリクスと進捗率計算を保持する。
   - 画面仕様の長期/中期/短期プランとホームの進捗表示を想定したフィールド（タイトル、期間、ステータス、メトリクス配列、継続日数など）を用意する。
2. **RecordingSessionState の計算ロジック**
   - 記録中の時間/距離/カロリー/心拍サンプルを保持し、目標値がセットされている指標について0〜1にクランプした進捗率を返す。
   - 心拍はサンプル平均を使用し、計測が無ければ進捗を未計算として扱う。
3. **TrainingLog 集計ヘルパー**
   - ログを日次/週次にグルーピングし、総時間（秒）、総ボリューム（重量×回数、ウォームアップ除外）、目的別のセッション数を計算する関数を追加する。
   - 集計ロジックをテストから直接呼べるユーティリティとして提供する。
4. **テスト駆動の確認**
   - 新規モデル/ヘルパーの契約をテストで先に定義し、失敗を確認した上で実装する。
   - 既存の UI 依存部に影響しない純粋ロジックで完結させる。

## ガイドラインチェック（着手前）
- ✅ アーキテクチャ境界を尊重し、Domain/Utilities のみに閉じたロジック追加とする。
- ✅ 新規外部依存や複雑なパターン（Repository/UoW）は導入しない。
- ✅ テストを先行させ、計算ロジックをユニットテストで保証する計画になっている。

## ガイドラインチェック（実装後）
- ✅ 計算ロジックは Domain 層の純粋関数・値オブジェクトとして実装し、他レイヤーへ波及する依存を追加していない。
- ✅ 新規ドキュメント（spec/plan/tasks/research/data-model/quickstart/contract、設計メモ）を更新し、画面仕様との整合を明記した。
- ✅ テストを先に追加し、進捗計算と集計ロジックの境界値をカバーした上で実装している。

## 検証計画
- `swift test` を実行し、新規テスト（プラン進捗、RecordingSessionState、TrainingLog集計）が通過することを確認する。
- ドキュメント（spec/plan/tasks/data-model/research/quickstart/contract）の更新内容を差分確認し、画面仕様との齟齬がないかレビューする。
