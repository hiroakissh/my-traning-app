# 記録セッションロジック 実装計画

## コンテキスト
記録画面にライブ計測と目標タイプ別バリデーションを追加し、`TrainingLog`まで保存するフローを構築する。既存ターゲット（`my_traning_app`/`my_traning_appTests`）内で完結させ、新規モジュールは追加しない。

## アプローチ
1. バリデーションロジックの抽出
   - `Domain/Services`に目標タイプ別の判定を行う小規模ユースケース（仮称：`RecordingSessionValidator`）を追加し、メニュー選択件数と経過秒数からCTA有効可否と理由を返す。
   - ユニットテストで各目的の条件と文言を先に定義し、TDDで進める。
2. タイマー状態管理の追加
   - 計測状態を保持するモデル（開始時刻・経過秒・実行/一時停止フラグ・最終更新時刻）をDomainに追加し、秒単位でのインクリメントとリセットを行う。
   - 表示用のフォーマッタを用意し、テストでカバレッジを確保する。
3. SwiftData 永続化との接続
   - `my_traning_appApp`に`modelContainer`を設定し、`TrainingLog`階層のモデルを登録する。
   - `RecordingView`から`ModelContext`を受け取り、保存時に`TrainingExercise`をメニューから生成するヘルパーを実装する。
4. UI への統合
   - `RecordingView`に目的ピッカー、バリデーションメッセージ、タイマーUI（開始/一時停止/リセット/終了して保存）を追加する。
   - CTAの有効状態がバリデーションと同期するようバインドし、保存成功時は状態をリセット・サクセスメッセージを表示する。
5. テストと検証
   - バリデーション・タイマー・TrainingLog生成のユニットテストを追加する。
   - `swift test`を実行し、結果を記録する。

## フェーズ1 憲法チェック
- ✅ 仕様の目標（バリデーション・タイマー連動・TrainingLog保存）に沿った分割になっている。
- ✅ アーキテクチャ境界を尊重し、ビジネスロジックはDomain、UIはPresentationに留める。
- ✅ 新規フレームワークや過剰な抽象化を導入しない。

## 検証計画
- 追加ユニットテストを含めて`swift test`を実行する。
- RecordingViewのプレビューでCTA無効化/有効化とタイマーの状態遷移を目視確認する。
- 保存成功・失敗それぞれのメッセージ表示をUI上で確認する。

## ロールバック計画
- SwiftDataスキーマ変更を伴わないため、問題発生時はブランチをリバートする。
