# 記録セッションロジック仕様

## 概要
記録画面において、目標タイプ（`TrainingPurpose`）に応じたバリデーションを実施し、条件を満たさない場合は主要CTAを無効化する。あわせてライブ計測タイマーと連動させ、開始・終了時刻と経過時間を`TrainingLog`へ保存するまでのフローを構築する。画面仕様（`design_docs/screen_specifications/02_recording.md`）に準拠し、利用者が目標に沿った記録を安全に完了できることを目的とする。

## 背景
- 現在の`RecordingView`はメニュー選択のみで、目標タイプの選択や開始ボタンのバリデーションが存在せず、「記録を開始」CTAは選択件数に関わらず有効になっている。
- ライブ計測用のタイマーや開始・終了時刻の保持がないため、`TrainingLog`の`sessionDurationSec`/`startTime`/`endTime`は保存されない。
- 保存処理の TODO が残っており、`TrainingLog`との接続が未完了。

## 目標
1. 記録開始前に目標タイプとメニュー選択状況を検証し、要件を満たさない場合はCTAを無効化する。
2. ライブタイマーを導入し、計測開始・一時停止・再開・リセットの各操作で秒単位の経過時間を更新する。
3. 計測終了時に`TrainingLog`へ`startTime`/`endTime`/`sessionDurationSec`と選択メニューを保存し、成功時はUI状態をリセットする。
4. バリデーション理由や保存結果をインラインで示し、利用者が次に取るべき行動を把握できるようにする。

## 非目標
- セット詳細（重量/回数/RPEなど）の入力UI実装。
- HealthKit連携やApple Watchとの同期、外部通知。
- AIプラン生成やプラン編集機能の変更。

## ユーザーストーリー
- 筋肥大目的で記録する利用者として、必要な種目数を満たすまで開始ボタンが無効化され、要件を確認したい。
- 減量目的で短時間の有酸素を行う利用者として、タイマーが実時間で進み、十分な時間が経過したときだけ保存できるようにしたい。
- 開発者として、計測開始/終了のタイムスタンプと所要時間が`TrainingLog`に保存されることを保証したい。

## 受け入れ条件
1. 記録画面に`TrainingPurpose`を選択するピッカーが表示され、未選択またはバリデーション未達成の場合「記録を開始」CTAは無効化される。
2. 目的別のバリデーションルールが適用される（開始ボタン判定）:
   - `hypertrophy`/`tune`: メニュー選択が2件以上であること。
   - `diet`/`refresh`/`other`: メニュー選択が1件以上であること。
   ルール未達の理由は画面内に文言で表示される。経過時間に関する要件は保存時の判定で適用する。
3. 「記録を開始」を押下すると現在時刻が`startTime`に設定され、ライブタイマーが1秒毎に増分する。`再生/一時停止/リセット`の各操作で表示と内部状態が同期する。
4. 「終了して保存」CTAは計測が開始され、目的別の最小時間を満たすまで無効のまま（`diet`: 600秒以上、`refresh`: 180秒以上、その他は開始済みであれば可）。押下時には`endTime`が設定され、`sessionDurationSec`は経過秒数に一致する。
5. 保存成功後、`TrainingLog`がSwiftDataに永続化される。`purpose`/`source=timer`/`startTime`/`endTime`/`sessionDurationSec`/`exercises`（選択メニューを`TrainingExercise`として`sets`空配列、`bodyPart=.other`、`category=.strength`で作成）が登録され、成功メッセージとともにフォームがリセットされる。
6. 保存時にModelContextのエラーが発生した場合、画面にエラーメッセージが表示され、計測状態と選択状態は保持される。

## 未解決事項
- タイマー計測中にアプリがバックグラウンドへ移行した場合の挙動（今回の範囲外のため留意のみ）。
- 減量目的で必要とする種目タイプ（有酸素など）の厳密な分類は未設定。現状は件数と時間で代替する。

## 依存関係
- SwiftDataのモデルコンテナ設定（`TrainingLog`関連モデルが対象）。
- `Resources/workout_menus.json`の読み込みに成功していること。
